# Target design: the game tape and the 3D viewer

Written 2026-11-15 on the user's direction, before the code. Branch `tape`, worktree `within-reason.tape`.

The user: "The in-game replay system of BAR relies on stepping the game forward in simulation for viewing any replay.
Our webui is the only thing that can inspect and easily step the game forward and back without that. Even then, it is
missing enough information that I frequently have to return to the real game replay engine to see what went wrong. I
would like for us to build our own replay format and viewer system that shows everything (3d environment, unit models,
projectiles, etc) the real game engine does, but allows full rapid seeking."

## 0. Rulings (the user, 2026-11-15, with his words)

| Question | Ruling |
|---|---|
| Fidelity | The engine's information, not its picture: "Information parity is the right target -- primarily maximizing how much information experienced humans can get out of watching it." |
| Renderer | WebGL2 written directly, no framework: "WebGL2 directly is a good goal for this -- webgpu still has spotty support when I last checked." |
| Capture | A Lua widget in the headless engine playing the demo: "Agreed with the lua widget for the capture system, and we will want to be able to easily run the game engine on a demo file to generate our new replay format from existing games." |
| The match record | Stays as it is (put to him as a departure from his "our existing replay format may be a good beginning"; he answered "Proceed"): the bot's fair view and its decisions, read by 74 scripts. The tape sits beside it and joins it by frame and unit id. |

Not asked again and still open: which moments sent him back to the engine. The stages below are in my order until he says.

**Chose / rejected.** A recording of state (chose: seeking is reading, the viewer holds no game logic) over
re-simulation from snapshots (rejected: needs the engine in the loop and a save/load the engine does not have) and
over video (rejected: a fixed camera inspects nothing). A widget (chose: no engine build, the same on every engine
version) over a patched engine (kept as the upgrade if the widget is too slow at 8v8 scale or exact animation is
wanted: one build per engine version, since a demo plays only on its own).

## 1. What is true today

- Three writers, JSON text, one sample a second or slower: the bot's `record-<seat>.jsonl` (own units' position and
  health, enemies seen, orders, decisions), the shim's `truth-<seat>.jsonl` (enemy units every 2 s), and for a demo
  `run/replay_match.py` with the widgets `replay_dump.lua` (the same files per team) and `audit_dump.lua`
  (`audit.jsonl`). The viewer is 3,300 lines of plain JS on a 2D canvas.
- Not in any of them: motion inside a second, heading, height, shots, projectiles; in arena games wrecks and the
  opponent's orders. A bot of `bots/` leaves no record at all: its games are seen only in the engine.
- The Erebos 10v8 (29 game minutes, peak 5,374 units, 2,321 of them mobile): 1.7 GB of records, 0.8 GB of truth files
  (two distinct contents in 18 files), 0.44 GB of audit; the replay took 36 minutes of wall.
- What a widget can read in a replay (engine source, `RecoilEngine-2026.07.04/rts/Lua`): every unit's position and
  its front, right and up directions (`GetUnitDirection`), health, orders; each weapon's direction
  (`GetUnitWeaponVectors`); the projectiles that exist (`GetProjectilesInRectangle`) with position, velocity, type,
  owner, target and time to live; features; the ground's heights. No event when a projectile is made or ends (synced
  code only), so the widget asks every frame. BAR's gadget `gfx_explosion_lights.lua` forwards explosions and muzzle
  fire to widgets (`VisibleExplosion`, `Barrelfire`) for eight weapon kinds. A widget reads any file of the game and
  the map through the engine's own archive layer (`VFS.LoadFile`).

## 2. The parts

```
demo.sdfz --(spring-headless + tape_dump.lua)--> tape.raw + assets/   (run/tape.py, run/replay_match.py --tape)
tape.raw  --(target/release/tape pack)---------> game.tape            (crates/tape)
game.tape --(run/view_match.py, byte ranges)---> the page: crates/tape-wasm (the same reader) + viewer/scene/*.js
```

1. **Capture**, `run/replay-template/LuaUI/Widgets/tape_dump.lua`: writes `tape.raw`, a run of records (a byte of
   kind, a u32 length, the payload). JSON for what is rare (the header, the tables of unit, weapon and feature types,
   events, orders, resources), packed numbers for what is not (unit samples, health, projectiles, the ground). It
   writes a unit's row only when the unit changed. It copies the files the viewer will draw with (models, textures,
   the map's files) out of the engine's archives into a cache named by content hash.
2. **The tape**, `crates/tape`: `tape pack` turns the raw stream into `game.tape`; the same crate reads it. Section 3.
3. **Assets**: served as the game's own files (`.s3o` models, `.dds` textures, the map's `.smf` and `.smt`) from the
   cache `run/data/tape-assets/<hash>`, which is git-ignored working data; the page parses them. BAR's licence
   (CC BY-NC-ND for most art) forbids derivatives: nothing of it is converted and committed.
4. **The viewer**: a WebGL2 scene in the map pane (`viewer/scene/`), the panels and the timeline as they are. The
   2D map stays as a mode until the 3D view carries its layers (stage 3).

## 3. The tape (`game.tape`, version 1)

One file a game, both sides, every seat. Little-endian.

```
magic "WRTAPE\1\0"
chunk*          kind[4] flags:u32 (bit 0: zstd) raw_len:u32 stored_len:u32 payload
footer          offset of the INDX chunk: u64, "WRTAPEND"
```

In file order: `HEAD` (JSON: versions, the map, teams, spots, the scales and intervals, the last frame, winners),
`DEFS` (JSON: the unit, weapon and feature types the game used, by the engine's id), `GRND` (the ground at the start:
u16 heights, one a corner of an 8-elmo square), `SLIC` x N, then the whole-game tables `UNIT`, `FEAT`, `TEAM`,
`EVNT`, `GPAT`, and `INDX`. The tables stand after the slices so that a tape still being written can grow: append a
slice, rewrite the tables, the index and the footer (stage 4; version 1 is written once, after the game).

**A reader's order**: the footer (the last 16 bytes), `INDX`, then `HEAD`, `DEFS`, `GRND` and the tables, then the
slice under the playhead and its neighbours. A seek is one slice.

**Whole-game tables.**
- `UNIT`: a row a unit life: the engine's unit id (the engine reuses ids; the row number is the tape's own id and
  everything in the tape names a unit by it), type, team, the frames it was created, finished and destroyed, who
  killed it, and for a type that cannot move its place and attitude. The timeline's lanes and the unit panel read it
  without opening a slice.
- `FEAT`: a row a feature (tree, rock, wreck): type, place, attitude, metal, the frames it appeared and went.
- `TEAM`: each team's metal and energy (store, income, pull, spend) once a second.
- `EVNT`: the rare events with their frames: a unit given to another team, chat, the end.
- `GPAT`: every change to the ground after the start, in order: a rectangle of heights with its frame. The ground at
  a frame is `GRND` with the patches up to it.

**A slice** covers `slice_frames` frames (300: ten seconds) and is decoded alone, given the tables:
- the **keyframe**: every unit alive at its first frame (row, health, build progress, paralysis, flags; position and
  attitude when its type moves), and every projectile in flight then;
- **motion**: for each unit that moved, its samples in the slice (every `sample_frames`, 3: the bot's own tick),
  stored as one run per unit, each column delta-coded (the frame steps, x, y, z, the front and the up direction);
- **vitals**, **activity** (the head order and what it points at, the queue's length, what a builder builds) and
  **aim**: a row when it changed;
- **orders**: every command given, either side;
- **projectiles**: one row each: the frames it began and ended, weapon type, owner, team, where it began, its
  velocity and gravity, what it was aimed at. A reader works a shell's or a laser's place out from that row; a
  projectile that steers (missile, starburst, torpedo, anything that wobbles) has its place sampled every
  `sample_frames` as well;
- **bursts**: explosions and muzzle fire (frame, place, weapon type, owner).

Positions are whole quarters of an elmo and an attitude is heading, pitch and roll in 4096ths of a turn, as varints
of the difference from the last value (section 6: the first build's eighths and two direction vectors cost 2.5 times
as much). Between samples the reader interpolates; projectile, burst and order rows carry their exact frames.

**The reader** (`crates/tape`, and `crates/tape-wasm` compiled for the page: a plain `cdylib` with a C interface,
no wasm-bindgen, built by `cargo build --target wasm32-unknown-unknown` and loaded by forty lines of glue) answers:
the state at a frame, as flat arrays the page hands to the GPU (units by type with position, attitude, team, health,
build progress, flags; projectiles; bursts of the last seconds); a unit's row and history; the events of a span.

## 4. The viewer (stage 1 target)

- The ground as a grid of patches whose heights the vertex shader reads from a texture (so a crater is a texture
  update), level of detail by distance, lit by the height texture's own slopes, coloured by the map's texture tiles
  (the `.smt`'s DXT1 blocks laid into one texture without recompression, the mip level that fits), water as a plane.
- Units as their models, one draw a type (instanced), the pieces at their rest pose, the team colour through the
  texture's alpha as the engine does; a nanoframe by its build progress; health as a bar when hurt. Far away a unit is
  the game's own icon, as in the game.
- A camera as the game's: pan, zoom about the cursor, turn and tilt.
- The playhead, the timeline, the panels, selection (a click picks the nearest unit under the cursor) as today;
  finer speeds and a step of one sample.

## 6. Status (2026-11-15, the day it was written)

**Stages 0 and 1 are built, and of stage 2 the projectiles, the flashes, health, build progress and the features.**
The format, the tools and the numbers: `docs/harness/tape-format.md`. What the page shows: `record-format.md`, Viewer.

What stage 0 found, each of which moved the design:
- **Replays ran at twice game speed for a reason that was not load**: a headless engine sleeps after each frame to
  hold the game's speed factor, and a demo's is 1. With the speed set first, a duel of 18.7 minutes is captured in
  46 s (24 s of it the game, 1.5 s the widget's own work) and a lobby demo's pre-game wait is gone. The record and
  audit replays got the same two commands (`replay_dump.lua`). "A big game is viewable a game's length after it
  ends", which the plan put to the user, is now about half that for the 10v8 and under a minute for a duel.
- **A headless engine gives a widget no explosion or muzzle-fire event** (BAR skips unsynced gadgets when headless).
  The reader draws a flash where a projectile ended and where a unit died; the tape's burst rows wait for stage 4's
  capture in a client with a screen.
- **Asking the engine every frame which projectiles exist is cheap and catches one-frame beams** (0.3 s of the
  duel's capture, 4.9 s of the 10v8's 835).
- **A shell and a bomb fly by the formula to under a tenth of an elmo; a laser bolt does not** (it stops where it
  hits and lingers): bolts are sampled like missiles.
- **Size.** The first encoding made the Erebos 10v8 156 MB (the plan had said 50 to 100 for motion): 103 of it
  motion, 21 aim. An experiment on the raw rows (`motion_size.py`, the session's scratchpad: the first 12 game
  minutes, 2.88 M samples, each column packed alone) priced the choices: two direction vectors in 16383ths 10.1 MB
  against heading, pitch and roll in 16 bits 4.0 and in 12 bits 2.5; places in eighths 3.1 MB, quarters 2.6, halves
  2.2. Chosen: quarters of an elmo (far under what a viewer or a measuring tool can see: a Pawn is 20 elmos wide) and
  4096ths of a turn (0.09 degrees). Captured again so, the 10v8 is 79.3 MB (motion 39.5, aim 8.9), the duel
  2.5 MB, and every one of the 10v8's 60.9 million unit states reads back the same as the raw stream.
- **Departures from the text above**: the assets are served as the game's own files and parsed in the page, as
  planned, and copied out by the widget through the engine's own archive layer, which the plan had not said (it finds
  each file whatever holds it and needs no reader of the archives' formats); `UNIT` rows carry the birth vitals; a
  slice keeps a projectile for `linger_frames` after its end so that the frames just after a slice's start can draw
  its flash.

Judged so far by: the round trip on every tape made (`tape pack --check`); `viewer/test/scene.js` in headless
Chromium on the duel (a bot's game: the tape alone) and on the flagship game (beside its record), with its
screenshots read; the 2D page's own test passing with a tape in the directory. **Not judged: by the user, on a game
he knows.**

Not built, in the order I would take them:
1. **Stage 3**, the 2D map's layers in the 3D view (section 7; 3a built 2026-11-15 night, 3b not).
2. **Aimed turrets and moving pieces.** The tape holds each weapon's direction (`--aim`); the page draws every model
   at its rest pose. Turning a turret needs to know which piece of a model a weapon turns, which the game's unit
   scripts hold; walking legs need those scripts run, or the pieces sampled, which a widget cannot do at 8v8 scale.
3. **Stage 4**: capture during an arena game; `truth-*.jsonl` and `audit.jsonl` read from the tape; a tape that grows.
4. Smaller: trees' own textures (TGA and PNG are not read: such a model is grey), the map's detail and normal
   textures, shields, the sea's surface as more than a plane.

## 7. Stage 3, the plan (2026-11-15, the user: "Let's continue with the next chunks in the order you see fit.")

The order I took, and why: what an experienced player reads off the game's own spectator view and the 3D view still
lacks, most-used first. Turrets and legs come after the capture in the arena (stage 4): under the fidelity ruling a
turned turret says little that the shot's own streak does not.

**3a, from the tapes as they are (no new capture):**
- **Orders.** The reader gives, with the state at a frame, each unit's head order with what it points at resolved to
  a place (a unit's place this frame, a feature's, the order's own), and the commands given in the last second and a
  half. The page draws the first as a thin line in the game's own command colours (every unit's with the layer on,
  the selected unit's always, with the footprint of what a builder is to build) and the second as the game's
  spectator view does: a line that fades.
- **A unit panel from the tape**, for any unit of either side and for a bot's game: what it is, whose, health, when
  and by whom it was built and killed, what it killed, its order and its queue's length, what it builds, its weapons.
  A selection is the tape's row (one life), not the engine's id (reused).
- **Ranges**: the selected unit's weapons, build reach and sight as rings on the ground; a layer for every static
  defence's reach.
- **Words over the scene**: a 2D canvas over the WebGL one, painted through the scene's projection by the same
  functions that paint the 2D map (the commander's and players' marks, the homes, the hands' groups, places and
  parties, the lane's ranks), so the two views cannot drift apart; the tape's own start places and metal spots.
- **A tape alone gets the side pane and the charts**: each side's income, stores and army worth from the tape's
  tables, so a bot's game has the same timeline a flagship game has.

**3b, with a second capture pass:** what each side could see of each unit (`GetUnitLosState` of the other ally teams,
which a spectator's widget may ask), drawn as the 2D map's "truth" layer was: what the chosen side did not see is
faint; the players' own map marks and pings (`MapDrawCmd`); the engine's unit limit (a feature's id in an order is
offset by it).

**Stays:** the 2D map, for every match made before the tape (a demo plays only on its own engine and game version,
so most of the archive can never be taped). "The 2D mode retired" (section 5) is now: no reason to leave the 3D view
in a match that has a tape.

**3a status (2026-11-15 night): built**, all five points, judged by `viewer/test/scene.js` in Chromium and Firefox on
the duel, the flagship game and the Erebos 10v8 (screenshots read) and the 2D page's test; not by the user. Found on
the way: repair, reclaim, resurrect and capture take five numbers when a builder working an area is on one target
(the target's id, then the area), and the widget's head order kept the first three, so the first build drew lines to
places far off the map; the reader now sorts the old tapes out by the ground's height (`aim_of`) and the widget
writes the target. `tape orders` lists any place off the map: none on the three games. With every unit's standing
order and every defence's reach on, the 10v8 draws about 21,000 lines a frame: legible on a part of the map, a smear
on the whole of it (both are off by default; the commands as given are on, as in the game).
